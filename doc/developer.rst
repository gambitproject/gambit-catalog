.. _updating-catalog:

Updating the catalog of games
=============================

This page includes developer notes regarding the catalog module, and the process for contributing to and updating Gambit's :ref:`catalog of games <catalog>`.
To do so, you will need to have the `gambit-catalog <https://github.com/gambitproject/gambit-catalog>`_ GitHub repo cloned and be able to submit pull requests via GitHub;
you may wish to first review Gambit's `contributor guidelines <https://gambitproject.readthedocs.io/en/latest/developer.contributing.html>`_.

You can add new games to the catalog, or edit existing ones that are saved in a valid representation `format <https://gambitproject.readthedocs.io/en/latest/formats.html>`_.
Currently supported representations are:

- `.efg` for extensive form games
- `.nfg` for normal form games

.. important::

   When updating the catalog, changes can be viewed by inspecting the documentation build generated by a pull request.
   You can also test changes locally.
   The catalog's tooling runs on the released versions of pygambit and gtdraw pinned in ``requirements.txt``:

   .. code-block:: bash

      pip install -r requirements.txt -r doc/requirements.txt

1. **Create or edit a game file:**

   Use either `pygambit <https://gambitproject.readthedocs.io/en/latest/pygambit.html>`_, the Gambit `CLI <https://gambitproject.readthedocs.io/en/latest/tools.html>`_ or `GUI <https://gambitproject.readthedocs.io/en/latest/gui.html>`_ to create (or edit) and save game in a valid representation `format <https://gambitproject.readthedocs.io/en/latest/formats.html>`_.
   Make sure the game includes a description, with any citations referencing the catalog's bibliography, ``references.bib``, using the ``:cite:p:`key``` format, e.g. ``:cite:p:`Rei2008```.

   .. important::

      If no bibliography entry exists, add one to ``references.bib``.

2. **Add the game(s) to the repo:**

   Create a new branch in the ``gambit-catalog`` repo.
   Each game is an *entry*: a directory inside ``games`` holding exactly one game file, named after
   the directory, together with that game's drawings.
   Add a new entry and commit it, or edit an existing game.
   The catalog uses a hierarchical folder structure that groups games by publication type and venue:

   .. code-block:: text

      games/
        books/{author-year}/{game}/{game}.efg              # games from textbooks
        journals/{venue}/{author-year}/{game}/{game}.efg   # games from journals (venue = geb, ijgt, mor, …)
        conf/{venue}/{author-year}/{game}/{game}.efg       # games from conferences

   The entry's directory path is the game's slug, used by the load function:

   .. code-block:: python

      pygambit.catalog.load("books/watson2013/exercise29_6")
      pygambit.catalog.load("journals/geb/bagwell1995")

   .. note::

      When adding a game from a **new** journal, conference, or other top-level category,
      add a human-readable label for the new hierarchy node(s) to
      ``hierarchy.yaml``.
      The catalog documentation page groups and labels games based on this file.
      Nodes without an entry fall back to a title-cased version of the folder name.

   .. important::

      The entry's directory path determines its "slug", used by the load function of the catalog module:

      .. code-block:: python

         pygambit.catalog.load("books/watson2013/exercise29_6")

3. **Add the game's drawing:**

   Every extensive game has a primary drawing, ``{game}.ef``, committed in its entry directory
   (e.g. ``games/source/game/game.ef``). It is the drawing the catalog's images, and the GUI, are
   made from. Make it once from the game with pygambit, using the catalog's layout options:

   .. code-block:: python

      import pygambit
      game = pygambit.read_efg("games/source/game/game.efg")
      game.to_gtdraw("games/source/game/game.ef", sublevel_scaling=0, shared_terminal_depth=True)

   Then curate it by hand if the layout needs work.
   Consult the `gtdraw docs <https://www.gambit-project.org/gtdraw/>`_ for the ``.ef`` format.
   If the game has an original layout from a published source (e.g. a textbook or journal article),
   you **should** try to capture that layout, either in the primary drawing or as a variant (below).

   The catalog's house style (``HOUSE_STYLE`` in ``build.py``) applies to every drawing.
   To change the style of one drawing, put a style block at the top of its ``.ef`` file, one line
   per option, e.g.:

   .. code-block:: text

      % gtdraw: action_label_dist 3.0

   **Layout variants:** To display multiple layout variants on the catalog page (rendered as
   clickable tabs), commit additional ``.ef`` files using the ``{game}__{label}.ef`` naming
   convention (double underscore separator), e.g.:

   .. code-block:: text

      games/example/game/game.ef                     # primary (tab label "Default")
      games/example/game/game__original_layout.ef    # additional (tab label "Original Layout")

   The label shown on each tab is derived automatically from the filename suffix: underscores
   are replaced by spaces and the result is title-cased (e.g. ``__alt_version`` → "Alt Version").

4. **Update the build files:**

   Use the ``build.py`` script to update the catalog's documentation and manifest, as well as generating images for the new game(s).

   .. code-block:: bash

       python build.py --build

   .. note::

      You can use the ``--regenerate-images`` flag when building the docs locally for a second time to force any changes to be picked up.

   .. warning::

      - The ``--build`` flag regenerates ``games/manifest.json``, the catalog's index: for each
        entry its game file and drawings, title, citation-resolved description, hierarchy grouping,
        and structural stats. Consumers such as pygambit and the GUI find files through it. It's a **committed** file, unlike
        ``doc/_table.rst``, since it needs to physically ship alongside the game files. A
        CI check fails if it's out of sync with the current catalog.

   .. tip::

      If stale generated images or tables prevent the build script or docs build working (step below), try running the following first:

      .. code-block:: bash

          git clean -fdX games/img doc/_table.rst

   .. tip::

      If the drawing of an extensive game needs work and you aren't sure which style options to change, try loading its ``.ef`` file in the gtdraw GUI and adjusting it there.
      There is an option to `download settings <https://www.gambit-project.org/gtdraw/gui/#exporting-and-reusing-settings>`_ which can be used in the Gambit catalog.

5. **[Optional] Test your updates to the documentation locally:**

   The previous step will (re)build your local copy of the Gambit Catalog RST page used by the documentation.
   Run the build from inside ``doc`` itself, not the repo root: the generated table
   embeds ``draw(...)`` calls whose paths are resolved relative to the current working
   directory, so building from anywhere else raises a file-not-found error.

   .. code-block:: bash

      cd doc
      sphinx-build -b html . _build/html

   Open ``doc/_build/html/index.html`` to view your changes.
   Iterate steps 2-4 as required.

6. **Submit a pull request to GitHub with all changes.**

   Submit a PR according to Gambit's `usual workflow <https://gambitproject.readthedocs.io/en/latest/developer.contributing.html#submit-contribution>`_.
   Ensure that any additions and changes to game files, ``references.bib``, ``hierarchy.yaml``, drawings, ``build.py`` and ``games/manifest.json`` are included.

   .. important::

      Even if you already checked the local docs build, ensure the catalog's own ReadTheDocs preview build on the pull request looks right.

.. _catalog-versioning:

Versioning and citing games
---------------------------

The catalog is a dataset, versioned independently of Gambit with
`semantic versioning <https://semver.org>`_, recorded in the ``VERSION`` file:

- **Major:** a breaking change to the manifest's schema.
- **Minor:** games added or removed, or a substantive correction to a game (its payoffs or structure).
- **Patch:** non-substantive fixes, such as typos in metadata or changes to a drawing's layout.

While the major version is 0, the schema may still change in a minor release.

A game is identified by its slug together with a catalog release, e.g.
``books/myerson1991/fig2_1`` in catalog 0.2.0, or together with a commit of this repository.
Games do not carry version numbers of their own: to use a game as it was before a correction,
use an earlier release.

The manifest
------------

``games/manifest.json`` is the catalog's index, generated by ``build.py --build`` and committed,
so every commit and release describes itself.
Its format is defined by the JSON Schema ``schema/manifest.schema.json``,
and ``schema_version`` in the manifest is the catalog's major version.
All paths in the manifest are relative to ``games/``.
The schema describes one release exactly; programs reading the manifest should ignore properties
they do not recognise, since a minor release may add some.

Making a release
----------------

A release is the archive ``gambit-catalog-<version>.zip`` and its SHA-256, attached to the
GitHub release for the tag ``v<version>``. The archive holds, under ``gambit-catalog-<version>/``:

- ``games/``: the manifest and every game file and drawing it lists;
- ``thumbs/<slug>.png``: a thumbnail of each game, at most 560 pixels on a side, made from its
  primary drawing (or its table, for a strategic game) in the catalog's house style;
- the schema, the licences and the README.

To build the archive locally (this needs ``pdflatex``, with the ``sgame`` package, and
``pdftocairo`` from poppler):

.. code-block:: bash

   python build.py --skip-table --release dist

To release:

1. Set ``VERSION`` to the new version, following the rules above, run ``python build.py --build``
   and commit both files.
2. Tag that commit ``v<version>`` and push the tag. The release workflow checks that the tag
   matches ``VERSION``, builds the archive and attaches it and its ``.sha256`` to the release.
